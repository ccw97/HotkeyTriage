# Windows 全局热键管理器 · 方案设计

> 版本 v3.2 ｜ 2026-10-20 ｜ 状态：需求已补充，进入设计阶段
> **取代** v2.0 与 v1.0。
> v3.0 的两处根本变更：① 产品从「单键诊断器」转为「全系统热键管理器」；② 定位手段从「知识库排序」转为「遍历探测归因」，知识库可取消。
> v3.1 的两处变更：① 确认存在「热扫描」方案（注入 + 模拟按键），作为**可选高级模式**引入；② 删除「临时禁用」表述，统一为「结束进程（可恢复）」。
> v3.2 的变更：**改为必须管理员权限启动**，以换取完整覆盖面；同时明确管理员「买得到覆盖面、买不到读取特权」的边界（§5.1）。

---

## 1. 一句话定位

> **一个不需要管理员权限、不注入进程、不装内核驱动，就能列出这台电脑上所有全局热键、并指出每个热键归哪个程序所有的 Windows 工具。**

上一版说"定位占用者"，这一版说"列出全部"——差别不在措辞，在于**产品从"出问题时才用"变成了"想看清就能看清"**。这是用户补充需求带来的实质性升级。

## 2. 需求变更记录（v2 → v3）

用户补充的 5 点需求，逐条落地方式：

| # | 用户需求 | 落地方式 | 影响 |
|---|---|---|---|

## 3. 第 5 点的技术回答（含实测）

这是本次最关键的架构问题。结论先行：**能取消，但要保留两条「规则」而不是「知识库」。**

### 3.1 实测：归属映射可以不靠知识库建立

```
阶段1  两个进程分别注册 F9、F10   → F9=taken  F10=taken   知道被占，不知是谁
阶段2  结束进程A                 → F9=free   F10=taken   归属确立
阶段3  恢复进程A                 → F9=taken  F10=taken   恢复后自动重新注册
阶段4  结束进程B                 → F10=free              归属确立
```

**三项全部成立**（脚本 `probe/attribution_lab.py`，可复现）。

原理：热键释放与进程生命周期严格绑定（v2 已实测）。所以「结束某进程 → 复测所有未归因键 → 哪些变 free，那些键就属于它」是一条**确定性的推理链**，不依赖任何外部数据。

### 3.2 三条可选路径的取舍

| 路径 | 能否给出完整映射 | 权限 | 是否关闭程序 | 风险 | 决策 |
|---|---|---|---|---|---|
| **A. 遍历探测**（本次实测） | ✅ 能 | 普通用户（管理员进程除外） | **会，逐个闪退** | 中（短暂打断） | ✅ **默认** |
| **B. 注入钩子 + 模拟按键** | ✅ 能 | **需管理员** | ✅ 不会 | **高**（注入行为；模拟按键会触发对方功能） | ⚠️ **可选模式** |
| C. 内核读热键表（OpenArk 式） | ✅ 最全 | 管理员 + 签名驱动 | ✅ 不会 | **最高**（驱动被 blocklist） | ❌ 否决 |
| D. ETW 监听 RegisterHotKey 调用 | — | — | — | — | ❌ **技术死路** |

**关于 B 的定位修正**：v3.0 把注入一律否决，是过度保守。B 确实能做到"不关闭程序"，只是需要管理员且会触发副作用。正确做法不是禁掉，而是**做成可选模式，默认关闭，且硬排除游戏与反作弊进程**。

**关于 D 为什么是死路**（这条很重要，省掉后人重复踩坑）：

Elastic Security Labs 反编译了 `win32kfull.sys` 中的 `NtUserRegisterHotKey`，确认**该函数内部没有任何 `EtwTrace*` 调用**——作为对照，`NtUserGetAsyncKeyState` 开头有 `EtwTraceGetAsyncKeyState`。所以 ETW 完全看不到热键注册事件。这条路在 Windows 10 22H2 上已被验证不通，不必再试。

**A 的代价必须写进产品文案**：它用"短暂打断应用"换取"零注入、零驱动、零风险"。B 和 C 更快更全，但把用户推到账号风险与驱动风险里——对一个兴趣驱动的免费工具，不值得。

### 3.3 「取消知识库」的精确边界

要区分两类数据，用户想取消的只是第一类：

| 类型 | 例子 | 是否需要持续维护 | 结论 |
|---|---|---|---|
| **知识库**（事实数据） | "weixin.exe 默认注册 Alt+A" | 是，软件一改就过期 | ✅ **可取消** |
| **规则表**（判定逻辑） | "Alt+Tab 是系统保留键"、"explorer.exe 是系统进程" | 否，Windows 大版本才变 | ❌ **必须保留** |

规则表回答的是"这是不是系统的东西"，靠**路径与签名**判定，不需要知道任何具体软件。例如：

```
判定 Windows 自带：进程路径在 %SystemRoot%\ 下 且 有微软签名
判定系统保留键：组合键在静态白名单中
```

这两条不需要维护，也不会腐化。取消它们会让树状视图的两个 tab 失去分类依据。

### 3.4 取消知识库的真实损失（必须知情）

知识库唯一不可替代的价值是 `disableHint`——**告诉用户"去微信设置 → 快捷按键里关掉"**。

| 能力 | 有知识库 | 无知识库 |
|---|---|---|
| 定位到进程 | ✅ | ✅（遍历法） |
| 永久关闭（引导改设置） | ✅ | ❌ 只能说"结束进程" |
| 定位速度 | 快 | 慢（需遍历） |
| 长期可用 | 会腐化 | 不腐化 |

**代价是产品从"解决问题"退到"临时止痛"。** 用户今天关掉微信，明天开微信又回来了。

### 3.5 建议的折中：知识库降为「可选增强」，不参与定位

不取消，但**降级到不影响任何核心能力的位置**：

- 定位 100% 靠遍历探测，**不看知识库**
- 知识库只做两件事：① 若命中，多显示一行"去这里可以永久关闭"；② 若命中，把它排在候选前面加速
- 知识库缺失/过期/损坏，**功能一点不少，只是少了一句建议**

这样既满足"技术上不依赖知识库"，又保住了那半句最有用的建议。代价是维护一份可选的 JSON，不维护也能用。

## 4. 七条已验证的事实

| # | 事实 | 证据 |
|---|---|---|
| 1 | Windows 无热键反查 API | 框架层面只有 `RegisterHotKey`，无 `EnumRegisteredHotKeys` |
| 2 | 挂起进程**不释放**热键 | 实测：`taken → 挂起 → 仍 taken → 结束 → free` |
| 3 | **遍历探测可建立归属映射** | 实测：结束 A 后 F9 释放，F10 未变 |
| 4 | 恢复进程后热键**自动重新注册** | 实测：重启 A 后 F9 重新 taken |
| 5 | 热键表在**内核空间**，用户态不可读 | `gphkHashTable` 位于 `win32kfull.sys`，OpenArk 与 Elastic 检测工具都需驱动才能读 |
| 6 | **ETW 看不到热键注册** | Elastic 反编译确认 `NtUserRegisterHotKey` 内无 `EtwTrace*` 调用 |
| 7 | 精准度与风险负相关 | 注入/驱动才够快够全，但触碰反作弊与系统稳定性红线 |

事实 5 与 6 合起来，证明了一件事：**"零权限、零注入、零驱动、不打断、还知道是谁"五个条件不可能同时满足。**

本产品的选择（v3.2）：**放弃「零权限」**（改为必须管理员，换取完整覆盖面）、**放弃「不打断」**（默认走遍历），并把「零注入」降级为可选模式。

**唯独「零驱动」永不放弃**——因为驱动是唯一能把风险从"用户体验"推到"账号被封 / 系统蓝屏"级别的东西，而它换来的额外收益（读内核热键表）已经可以通过遍历获得。

事实 2 直接决定了第 3 点需求的实现方式：**「临时禁用」只能是"结束 + 可恢复"，不存在"暂停"**。

## 5. 产品形态

**形态**：单文件 exe，免安装，双击即用，退出无残留。

| 铁律 | 含义 |
|---|---|
| **必须管理员** | 以 `requireAdministrator` 启动。这是"完整列出"的前提，不是可选项（v3.2 变更） |
| **零注入（默认）** | 默认不向任何进程写入代码。唯一的例外是可选的「快速识别模式」，须用户显式开启并知晓风险（§7.4） |
| **零驱动（永不破例）** | 任何模式下都不加载内核组件。读内核热键表一律不做 |
| **可恢复** | 任何被结束的进程都能一键拉起 |

### 5.1 为什么必须管理员，以及它到底买到了什么

**必须先把一件事说清楚，否则会误判这个决定的价值**：

> 管理员权限解决的是「够不着」，**不是**「看不见」。

| 管理员权限能做到 | 管理员权限**做不到** |
|---|---|
| 结束以管理员身份运行的进程（否则跳不过去，只能标注"无法确认"） | **读不到内核热键表**（`gphkHashTable` 在 `win32kfull.sys`，必须驱动，见事实 5） |
| 向提权进程注入钩子（快速识别模式才能覆盖它们） | **无法枚举热键注册**（无此 API，见事实 1） |
| 读取部分受保护进程的完整路径 | **碰不到 PPL 保护进程**（反作弊、杀软，即使管理员也打不开） |

**所以管理员权限买到的是"覆盖面"，不是"读取特权"。** 这是本产品诚实性的重要一环：不能因为提权了，就暗示"现在什么都能看到"。

**必须付出的代价**（必须写在 README 与首次启动说明里）：

| 代价 | 说明 |
|---|---|
| 每次启动弹 UAC | 用户信任门槛显著上升，这是"必须管理员"最真实的成本 |
| 杀软更敏感 | 「高权限 + 枚举进程 + 结束进程」是最典型的高危行为组合，误报概率上升 |
| 破坏力变大 | 提权状态下若 Guard 有 bug，可能结束系统进程导致会话崩溃 |
| 无法自证清白 | 用户难以验证"你提权后到底做了什么"，只能靠代码审计或签名背书 |

**正因如此，提权之后安全闸门必须从"尽力"变成"绝对"**（见设计文档 §5.4）。**权限越大，越不能只靠自觉。**

### 「临时禁用」的准确定义（回应需求 3）

用户说的"临时禁用"，在本产品的实现是：

```
临时禁用 = 结束该进程 + 记录完整启动信息 + 在列表中标记为「已禁用」
         ≠ 挂起进程（实测无效：热键仍被占用，且按键被静默吞掉）
         ≠ 禁止开机自启（那是永久性的）
```

恢复方式：列表中点"恢复"，或关闭工具时统一恢复，或下次启动时提示"上次禁用的 3 个程序尚未恢复"。

## 7. 三种扫描模式（解决"要列表就得打断应用"的矛盾）

需求 2 要求"启动后立即罗列"，但建立归属映射需要额外动作。三种模式各有取舍，**由用户按场景选**：

| 模式 | 做什么 | 耗时 | 关闭程序 | 需管理员 | 注入 | 输出 |
|---|---|---|---|---|---|---|
| **快扫** | 只做探测（828 组合） | < 1 秒 | ❌ | ❌ | ❌ | 未归属的键列表：哪些键被占 |
| **深扫** | 遍历候选进程，逐个结束复测 | 10–40 秒 | ✅ 逐个闪退 | ❌ | ❌ | 完整归属映射（确定性） |
| **快速识别** | 注入钩子 + 模拟按键 + 捕获 `WM_HOTKEY` | 2–5 秒 | ❌ | ✅ | ✅ | 完整归属映射（确定性） |

### 7.4 快速识别模式（v3.1 新增，解决"不打断"）

这是对"有没有热扫描方案"的正面回答。**有，原理如下**：

```
1. 向会话内所有同位数 GUI 进程注入钩子 DLL（WH_GETMESSAGE）
2. 用 SendInput 依次模拟按下每个待归因的组合键
3. 系统匹配热键表 → 向注册者投递 WM_HOTKEY
4. 注入的钩子捕获到「哪个进程收到了哪个 WM_HOTKEY」
5. 汇总 → 完整归属映射
```

**它能做到"不关闭任何程序"，但代价必须写清**：

| 代价 | 说明 |
|---|---|
| 需要管理员权限 | 否则提权进程的热键看不到 |
| 需要注入 | 杀软可能拦截；反作弊敏感 |
| **模拟按键会触发占用者的功能** | 微信会弹出截图框、录屏软件会开始录、音乐播放器会切换歌曲 |
| 受保护进程注入不进去 | 游戏、反作弊保护的进程查不到 |
| 32/64 位需各注入一套 | 32 位 DLL 进不了 64 位进程，反之亦然 |

**关键取舍**：它是"不关闭程序"，但不是"零打扰"——模拟按键会真的触发别人的功能。所以体验上，深扫是"程序闪退一下"，快速识别是"桌面上一堆窗口闪一下"。

**产品决策**：

- 默认**不启用**，藏在"高级"里，开启时弹一次风险说明
- 硬编码**排除游戏进程与反作弊组件**（即使注入失败也要求拦截）
- 识别完成后立刻卸载所有钩子，不留驻
- 若检测到当前有反作弊进程在运行，**禁用此模式并说明原因**——这是唯一一处宁可少一个功能也要保安全的判断

### 7.5 遍历范围优化（不改技术路线，直接减少打断）

即使不用注入模式，深扫也可以通过收窄候选来减少打断：

**依据**：`RegisterHotKey` 通常由有 GUI 线程的进程注册。实测本机 129 个占用里，第三方只占 14 个，对应的进程通常只有 3–6 个。

**收窄规则**（按优先级）：

1. 只取"有可见窗口或有托盘图标"的进程 → 通常 8–12 个
2. 再按知识库权重（若可用）排前 → 命中常在 1–3 个内
3. 若前 3 个已归因完所有键 → **提前结束，剩余进程不碰**

**效果**：典型场景从"关闭 20 个进程、40 秒"降到"关闭 3–5 个、10 秒内"。这是零成本的改动，优先级高于做注入模式。


### 7.6 交互设计

- 启动即快扫，立即呈现"Windows 自带"tab（系统规则表可直接分类，**无需深扫**）
- "其他应用"tab 显示："检测到 14 个热键被第三方占用"，并提供两个入口：「深度扫描」（不注入、会闪退）与「快速识别」（需管理员、不闪退但会触发功能）
- 深扫前必须弹确认：「将临时关闭 5 个后台程序，扫描完成后自动恢复」，列出清单
- 扫描可随时中止，已扫描部分保留结果

### 7.7 为什么系统 tab 不需要任何扫描

系统热键由 `explorer.exe` / `dwm.exe` 等少数进程注册，规则表可直接按组合键映射到功能名，不需要知道是哪个进程，更不需要结束它们（也绝不该结束）。

| 遍历归因时的安全闸门（黑名单、双轨） | 安全 |
| 快速识别：注入钩子 + 模拟按键，不关闭程序（**可选，默认关闭**） | 需求 5 延伸 |
| 可选的 `disableHint` 建议（知识库存在时） | 折中方案 |

### 不做

| 不做 | 原因 |
|---|---|
| **内核驱动 / 读热键表** | 永不破例。签名、稳定性、被 blocklist，且与"可验证承诺"冲突 |
| **向游戏或反作弊进程注入** | 即使启用快速识别模式，这两类也硬排除。这是账号红线 |
| 默认启用注入 | 注入必须由用户显式开启并看到风险说明 |

| 联网 / 众包 | 纯离线是既定约束 |
| 键位重映射 | PowerToys 已做得很好 |
| 开机自启常驻 | 与"双击即用、退出无残留"冲突 |
| 游戏模式自动进出场 | 场景已扩展为通用，不再需要 |
| 硬性依赖知识库 | 需求 5 |

## 9. 场景扩展（回应需求 4）

v2 把产品绑在"游戏玩家"上，这个定位过窄。修正后：

| 场景 | 典型冲突 | 本产品的作用 |
|---|---|---|
| 游戏 | 微信 `Alt+A`、显卡驱动 `Alt+Z` | 定位并临时禁用 |
| 办公 | 输入法 `Ctrl+Shift`、截图工具 `F1` | 看清谁占了，改键或禁用 |
| 开发 | IDE 快捷键与系统热键撞车 | 全景地图，规划自己的键位 |
| 多任务 | 不知道 `Ctrl+1` 被谁吃了 | 地图直接看 |
| 装机/排查 | 新电脑被预装软件抢键 | 一次扫描看清全部 |

**反作弊仍是硬约束，但不再是产品支点**：零注入零驱动的价值从"游戏专用"升级为"任何场景都不该有的风险"。

## 10. 关键设计抉择

| 抉择 | 采纳 | 否决 | 理由 |
|---|---|---|---|
| 权限模型 | **必须管理员** | 零权限 | 零权限下提权进程的热键无法归因，地图天然残缺。代价是 UAC 与杀软敏感度（§5.1） |
| 归属手段（默认） | 遍历探测 | 注入 / 内核 | 遍历零注入零驱动；在管理员权限下可覆盖提权进程 |
| 归属手段（可选） | 注入 + 模拟按键，默认关闭 | 一律禁掉注入 | 存在更优手段却彻底禁用是意识形态；正确做法是默认关、显式开、风险可见 |
| 知识库 | 可选增强 | 取消 / 强依赖 | 取消会丢失"永久关闭"建议；强依赖会腐化 |
| 扫描时序 | 快扫 → 深扫 | 启动即深扫 | 不能一打开就关用户一堆程序 |
| **"临时禁用"的语义** | **结束进程 + 记录恢复** | 挂起进程 | 实测挂起无效（事实 2），且会让按键被静默吞掉，比原来更糟 |
| 系统分类 | 路径 + 签名规则 | 知识库枚举 | 规则不腐化，且能覆盖未来新软件 |
| 深扫触发 | 用户显式确认 | 自动执行 | 批量关闭必须知情同意 |
| 遍历范围 | 先收窄再遍历 | 全量遍历 | 实测第三方只占 14/129，收窄后典型只需关 3–5 个进程 |

## 11. 成功标准

| 指标 | 目标 |
|---|---|
| 快扫耗时 | < 1 秒 |
| 快扫输出的热键数 | 与本机实际注册数一致（基线：828 组合中 129 个） |
| 深扫耗时 | ≤ 40 秒；收窄候选后典型 ≤ 15 秒 |
| 深扫归属准确率 | 100%（遍历是确定性的） |
| **提权后仍无法归因的键** | **≤ 3 个**（仅 PPL 保护进程导致；超出说明闸门过严或收窄规则有问题） |
| 深扫后恢复成功率 | 100% |
| 触碰反作弊/系统关键进程 | 0 |
| 冷启动（含 UAC） | ≤ 3 秒 |
| 单文件体积 | ≤ 50 MB |

## 12. 诚实声明（写入关于页）

| 查不到的情况 | 原因 |
|---|---|
| 钩子型占用（AHK、部分录屏工具） | 它们不注册热键表，本质不在"全局热键"范畴 |
| 驱动级 / OEM 硬件热键 | 内核层改写，用户态不可见 |
| 输入法截获 | 不属于热键机制 |
| **PPL 保护进程的热键**（反作弊、杀软） | **即使管理员权限也打不开这些进程**，遍历与注入都够不到。标注"受保护，无法确认" |
| 深扫被打断时的未归因项 | 用户中止或进程无法结束 |

> 注意：提权之后，「管理员权限进程的热键查不到」这条已不再成立——这正是本次改为必须管理员的直接收益。剩下的天花板只有 PPL 保护进程一类。

**原则**：明确说"查不到"，不给似是而非的答案。这个品类的用户已经被模糊答案折磨够了。
